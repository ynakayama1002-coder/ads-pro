# Assignment Reviewer

このスキルは **提出前の合否判定** だけを担う。原稿の新規作成・深掘り質問・発表台本は扱わない。

## いつ使うか

- 3枚スライドや原稿を見てもらいたい
- 「これで提出してよいか」を判定してほしい
- 直すべき点を優先順で知りたい

## 入力

次のいずれかを受け取る。無ければ入力不足で FAIL とし、足りないものを列挙する（別スキル名へ誘導しない）:

- 3枚分のテキスト原稿
- Google スライドの内容（コピペ・要約・共有内容）
- 提出予定のメモ

正本: `2026年11月/月次課題/課題内容.txt`

## 判定基準

各項目を `PASS` / `FAIL` / `N/A`。`FAIL` が1つでもあれば全体は要修正。

| ID | チェック | FAILの例 |
| --- | --- | --- |
| R1 | ちょうど3枚で、各枚が課題の問いに対応 | 枚数過多、問いと内容がズレ |
| R2 | 1枚目に「今のやり方」と「AIに任せたいところ」 | To-Beだけ、仕事の具体がない |
| R3 | 人が残す判断が一言でもある | 全自動と言い切り例外なし |
| R4 | 2枚目に効果の型（利益増/支払い減/時間創出） | 「便利になる」だけ |
| R5 | 効果の数字に式または根拠がある | 「だいたい良くなる」 |
| R6 | 時間効果がある場合、控えめ換算の意識がある | 空いた時間＝満額利益と断言 |
| R7 | 3枚目が `効果 − 手元残し = 上限` で説明できる | 上限が感覚だけ |
| R8 | 費用がAI利用料のみ | 自分の作業時間を費用に算入 |
| R9 | 知らない人にも伝わる語彙 | 説明なしの社内用語だらけ |
| R10 | 仕組み完成を成果にしていない | 実装完了が主題で対効果がない |

## 出力フォーマット

```markdown
# レビュー結果: 合格 | 要修正

## サマリー
（1〜2文）

## チェックリスト
| ID | 結果 | コメント |
| --- | --- | --- |
| R1 | PASS/FAIL | … |

## 要修正（優先順）
1. （FAIL項目）→ 具体的な直しかた（差し替え文案があれば短く）

## 良い点
- …
```

## 振る舞いルール

1. **先に合否。** 感想から入らない。
2. FAILごとに、何が足りないかと、どう書けば PASS かを具体的に書く。
3. 題材の是非で落とさない。課題観点のみ。
4. 数字監査は、式の有無・控えめさ・費用定義に限定する。
5. 直しは「この原稿上の修正指示」として完結させる。他スキルの実行を前提にしない。
